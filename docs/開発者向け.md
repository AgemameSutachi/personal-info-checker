# 開発者向けの説明

ソースから動かす・配布版を組み立てる・試験する・中の作りを知りたい人向けです。使い方は [README](../README.md) を見てください。

## ソースから動かす

64bit の Python 3.11 以降（Windows）で動きます。

```
python -m pip install -r requirements.txt

python -m pii_checker app       # アプリ版（窓）。引数なしでも同じ
python -m pii_checker serve     # Web 版（合言葉入りの URL を表示してブラウザを開く）
python -m pii_checker scan \\nas01\総務 -o 結果.xlsx --csv   # コマンド版
```

コマンドの引数・終了コードは [詳しい説明](詳しい説明.md) の「コマンドの引数・終了コード・定期実行」と同じです（`PiiChecker-cmd.exe` を `python -m pii_checker` に読み替える）。

rar・lzh・AES 暗号の zip・ディスクイメージ（ISO・VHDX 等）は 7-Zip で開きます。7z.exe は `scan --sevenzip` の指定 → 実行ファイルの隣 → Program Files → PATH の順に探し、無ければそれらの形式は理由つきで「検査不能」になります。

## 配布版（exe）を組み立てる

`python build.py` で `dist/PiiChecker/` に作ります（約 310MB・zip にすると約 160MB。1.4.0 で測った値）。

組み立てる PC に要るもの:

- requirements.txt の依存と PyInstaller（`python -m pip install pyinstaller`）
- 7-Zip（`C:\Program Files\7-Zip` に入れるか、`7z.exe`・`7z.dll`・`License.txt`・`readme.txt` を `vendor/7zip/` に置く。`vendor/` はリポジトリに含まないので自分で作る）。見つからないと同梱せずに組み立てを続ける（配布先に 7-Zip が要る）
- 32bit の Python 埋め込み版は python.org から自動で取得する。取れない環境では `--python32-zip <python-3.12.x-embed-win32.zip>`で渡すか、`--skip-python32` で省く（省くと Access 97 や 32bit のドライバしか無い PC で Access を読めない）
- Java 実行環境と Jackcess（Access の中身の対処で、ACE の無い .accdb を書き換える手段）: Eclipse Temurin の JDK 21 を GitHub から、Jackcess 4.0.8・commons-lang3・commons-logging を Maven Central から自動で取得する（SHA-1・SHA-256 を公開値と照合する）。置き場はビルド用のキャッシュ `build/cache/`（環境変数 `PIICHK_BUILD_CACHE` で変えられる）。手元の JDK を使うなら `--jdk-dir <JDK 21 のフォルダ>`（環境変数 `PIICHK_JDK` でも）、省くなら `--skip-java`（省くと、ACE の無い PC では .accdb の中身を書き換えられない）。`tools/jackcess/AccessRewrite.java` を `--release 11` でコンパイルして `piichk-access.jar` にし、`jdeps` で調べたモジュールだけの Java 実行環境を `jlink` で作る（約 48MB）
- 補助を exe にした版（access32_helper.exe）が欲しいときは、32bit の venv に pyinstaller を入れて`powershell -ExecutionPolicy Bypass -File build_helper32.ps1 -Python <32bit の python.exe>`（dist_helper32/ に作る）

できあがるもの:

- `PiiChecker.exe` … デスクトップアプリ。WebView2 が無い・窓を作れない PC では同じ画面を既定のブラウザで開く。引数にフォルダ・ファイルのパスがあれば（ドラッグして離す・「送る」）、それを対象の欄に入れて窓を開く。受け付けるのは `--db` とパスだけで、`scan` などが渡ってもコマンドの処理へは入らない（コマンド版を使うよう窓で知らせる）
- `cmd/PiiChecker-cmd.exe` … コンソールで使う版（`serve` で Web 版、`scan` などでコマンド版）。一番上でダブルクリックできる exe をアプリ版の1つだけにするため下のフォルダに置き、部品は親の `_internal` から読む（PyInstaller の `contents_directory` は1階層の名前しか受け付けないので、起動部が読む設定 `pyi-contents-directory ..\_internal` を spec で直接埋めている。build.py が毎回起動して確かめる）
- `_internal/7z/` … 7-Zip（VHDX・zstd 等もこれで開く）
- `_internal/python32/` … 32bit の Python 埋め込み版と Access 補助（読み取り用 `access32_helper.py`・書き換え用 `access32_rewrite.py`）
- `_internal/java/` … Java 実行環境（OpenJDK 21 を jlink で小さくしたもの。`legal/` に許諾文）
- `_internal/jackcess/` … Jackcess・Apache Commons の jar・補助の jar（`piichk-access.jar`）・`licenses/`
- `LICENSE.txt`・`THIRD-PARTY-LICENSES.txt` … このツールと、同梱する依存のライセンス文（配るときはフォルダごと渡す）
- `はじめにお読みください.txt` … 画面の版とコマンド版の使い方（配布の zip に README は入れない）

Jackcess・Apache Commons（Apache 2.0）と OpenJDK（GPLv2 + Classpath Exception）の許諾文は、THIRD-PARTY-LICENSES.txt の末尾に入れる（`java_license_section`）。組み立ての最後に、同梱の Java 補助を実際に起動して確かめる（`check_java`）。開発・試験用に `python build.py --fetch-jackcess` で Jackcess の jar を `vendor/jackcess/`（リポジトリに含まない）へ取り込める。exe を作らずに Java の取り込みだけ確かめるには、`build.DIST`・`build.INTERNAL`・`build.WORK`・`build.CACHE` を作業用のフォルダへ向けて `build.add_java(<JDK のフォルダ>)`・`build.check_java()`・`build.java_license_section()` を呼ぶ（tests/test_build_java.py は、ネットワークも JDK も使わず、取り込みの部品だけを試す）。

AGPL-3.0 の全文は PyMuPDF の配布物に含まれないので、`licenses/AGPL-3.0.txt` の写しから THIRD-PARTY-LICENSES.txt に入れます。

### Rust 拡張（pii_rs_detect）

本文の検出（`detectors.detect` の正規表現と手がかり語の判定）の中心は、Rust の拡張 `rust/pii_rs_detect/`（PyO3・regex）でも動きます。目標は Python 版（`detectors._detect_py`）と同じ結果を返すことで、大きなファイル（Oracle のダンプなど）の検出が速くなります。同じ結果になっていることは、下の「等しさの確認」の範囲で確かめています（全部の入力で保証するものではありません）。

- 作り方: `python tools/build_rust_ext.py`(cargo と maturin が要る。maturin は requirements-dev.txt に入っている)。wheel を作って、いま動かしている Python の環境へ入れる。`python build.py` も exe を作る前にこれを呼び、拡張が入った状態の exe を作る(`dist/PiiChecker/_internal/pii_rs_detect/pii_rs_detect.cp311-win_amd64.pyd` が入る)。`--require-rust` を付けると、拡張を作れなければ失敗にする。CI の `test` も作って入れてから試験する
- 作った環境のパスを埋め込まない: rustc は panic の位置として依存の crate のソースのパス（`CARGO_HOME` の下の registry。既定は利用者フォルダの下）を拡張に埋め込む。`tools/build_rust_ext.py` は `CARGO_HOME`・rustup のホーム・リポジトリの3つを `--remap-path-prefix` で `/cargo-home`・`/rustup-home`・`/pii-checker` へ写して組む（`CARGO_ENCODED_RUSTFLAGS` で渡す。既にある `RUSTFLAGS` は空白で割って引き継ぐ。cargo はこの変数があると `.cargo/config.toml` の `rustflags` を読まないので、そこに書いた指定は効かない）。写すのは先頭だけなので、埋め込まれた文字列は `/cargo-home\registry\src\…` のように後ろが Windows の区切りのままになる。入っている拡張にホームやリポジトリのパスが残っていれば tests/test_rust_patterns.py が落ちる。maturin を直に打つとこの写しが付かないので、配布に入れる拡張は必ずこの台本で作る
- 無いときの動き: 拡張を import できない(cargo が無く作れなかった・入れていない)、または環境変数 `PII_CHECKER_NO_RUST` が空でないときは、今までどおり Python の `re` で検出する。どちらで動いているかは `PiiChecker-cmd --version` の2行目(検出エンジン。Rust を使っていなければ理由も出る)か `detectors.rust_enabled()`・`detectors.rust_status()` で分かる。拡張が想定外の失敗(panic など)をしたときは、その場から Python の経路に切り替え、理由を `%LOCALAPPDATA%\PiiChecker\engine.log` に1行追記する(画面の版や作業用プロセスには標準エラーが無く、警告が見えないため。読めない・壊れた拡張や同梱の範囲の表もここに残る)
- 正規表現の表: Rust の regex は先読み・後読みが使えないので、`detectors.py` の式を Rust 向けに書き換えた表 `rust/pii_rs_detect/src/patterns.json` を拡張に埋め込む。**`detectors.py` の式・手がかり語を変えたら、`python tools/export_rust_patterns.py` で表を作り直し、`python tools/build_rust_ext.py` で拡張も作り直す**。忘れると tests/test_rust_patterns.py が落ちる(`--check` で食い違いだけ調べられる)
- Rust で扱わず Python に回す本文: (1) Python の `\b`・`\w` と Rust の `\w` が語の文字とみなす文字は食い違う(² ³ と結合文字など)。`\s` の範囲も違う。(2) `RE_LANDLINE_INTL` の途中の先読み `(?![5789]0)` は、Python が「+81」の後ろの括弧・0 を取り直して通る場合があり、Rust では再現できない。(3) 単独のサロゲートを含む本文は Rust の文字列にできない
- (1) の扱い: 両者の判定が食い違う文字の範囲を両方向で求め(約 0.15 秒)、その文字を含む本文(見出しも)は Python で検出する。範囲は拡張を作るときに求めて `pii_checker/_rust_guard.py`(リポジトリに入れない)に同梱し、Python の Unicode データの版と拡張の Unicode の表の版が一致するときだけ使う。一致しなければ起動時にその場で求める
- (2) の扱い: 「+81」のあとに、区切り・括弧・0 を挟んで `[5789]0` が続く形を含む本文は Python で検出する(携帯の「+81 90-…」を含む本文もこちらに回る)。(3) の本文は 1 件ごとに Python で検出する
- 大文字小文字の畳み込み(ſ・K・ı・İ)は、表の段で書き換えて合わせてある
- 等しさの確認: tests/test_rust_equivalence.py が Python 版と Rust 版の結果を比べる(拡張が無ければ飛ばす。種の入力・ファズ 4,000 件・語の境目・「+81」の組み合わせ・大文字小文字・サロゲート・拡張が失敗したときの退路)。拡張を作り直したときは、全 Unicode の 1 文字を語の境目の前後に置く総当たり(約 1300 万入力・十数分)と、手元の入力の突き合わせも手で流す。直近の確認: 総当たり 13,344,768 入力・試験の入力 46,393・言語比べ 1,240 まとまり・Oracle ダンプ 240,972・ファズ 200,000(種 2 つ)で違い 0(このうち Python に回ったのは、総当たりで 154,908、言語比べで 107、ファズで約 4%)

## 試験

```
python -m pip install -r requirements.txt -r requirements-dev.txt -c constraints.txt
python -m pytest tests -q
```

- 環境によって飛ばす試験がある: `test_git.py` は git が無いと、`test_ocr.py` は日本語の OCR が無いと飛ばす
- `tests/test_folderacl.py` は tmp_path の下に作ったフォルダだけ、`icacls` で Everyone の読み取りを付けて外す（ほかの場所の権限は変えない）
- `tests/test_remote.py`・`tests/test_web_connection.py` は、手元に pyftpdlib の FTP サーバーを立てて接続方式を試す
- 検体（架空の個人情報を仕込んだファイル）は試験がその場で一時フォルダに作る。Office は要らない。7-Zip を使う試験が1件あり、`vendor/7zip/7z.exe` が無ければ飛ばす
- `tests/test_access32_helper.py` は 32bit の Python で動かす試験で、64bit では飛ばす（`<32bit の python.exe> -m pytest tests/test_access32_helper.py`。32bit の Python にも pytest を入れておく）。.accdb を作る段は、64bit の Python（環境変数 `PIICHK_PYTHON64`。既定は `~/temp/venv/personal-info-checker/Scripts/python.exe`）に pywin32 があり、Access のドライバ（ACE の DAO）があるときだけ動く
- 開発中（exe でない）の Access 補助は、32bit の Python を環境変数 `PIICHK_PYTHON32` →`~/temp/venv/personal-info-checker-32` → `%LOCALAPPDATA%\Programs\Python\Python3*-32` の順に探す
- `tests/test_remediate_access.py`（Access の対処）は、使える手段（ACE・Jet・Jackcess）ごとに各方法を試し、無い手段は飛ばす。検体は ODBC のドライバの設定 API（`SQLConfigDataSourceW` の `CREATE_DBV12`・`CREATE_DBV4`）で空のファイルを作って SQL で埋める（ACE が無ければ Jet の 32bit 補助か Jackcess で作る）。Jackcess の試験は、環境変数 `PIICHK_JACKCESS_DIR`（jar が4つ揃ったフォルダ）が無ければ、`vendor/jackcess` の jar と `tools/jackcess` のソースを試験の中で `javac` でビルドして使う（JDK が PATH に要る）。表以外のオブジェクト（クエリ・リレーションシップ・索引）が残ることは DAO（pywin32。無ければその確認だけ飛ばす）の集まりで数える
- 大量の検体での回帰試験は `tests/make_corpus.py <出力先>`（Office の COM・7-Zip 等で検体を作る。pywin32 が要る）→ `tests/corpus_check.py`
- 検査の速さを版どうしで比べるのは `tools/bench_scan.py`。ドライブ丸ごとの検査の時間は、その時の PC の混み具合（メモリの圧迫・ほかの重い処理）で大きく揺れ、版の違いと切り分けられないため、毎回同じ中身になる材料（乱数の種を固定・11 形式・12 ファイル・架空の個人情報）を1つのプロセスで1ファイルずつ直列に、繰り返しの最小値で測る（同じプロセスで繰り返すので、覚え書きのキャッシュが温まった後の値）。
  `make <材料>` で材料を作り、`run <材料> -o <結果.json> --repeat 3` で測る。古い版は `git worktree add --detach <フォルダ> <タグ>` で取り出し、`ext <フォルダ> <展開先>` でその版の Rust 拡張を組んで（cargo と maturin が要る。venv の拡張は入れ替えない。worktree が深い所にあって link.exe が LNK1104 で落ちるときは、環境変数 `CARGO_TARGET_DIR` を短いパスにする）、`run … --code <フォルダ> --ext-dir <展開先>` で測る。
  `compare <基準.json> <比べる.json>` がファイルごとの時間の比と検出の件数の差を並べる。合計は両方とも問題なく検査できたファイルだけで出し、検出のエンジン（Rust 拡張の有無）や Python の版が違えば「！」の行で知らせる。ほかの処理が CPU を使っている PC では同じ版でも揺れるので、版を交互に（A→B→A→B）測って同じ版の2回のずれも見る。
  `tests/test_scan_speed.py` は、ふだんは小さな材料で「どの形式も検査でき、仕込んだ値を見つけ、1ファイルが遅すぎない」ことを確かめる。環境変数 `PII_CHECKER_BENCH_BASELINE`（基準の結果）と `PII_CHECKER_BENCH_CORPUS`（その材料）を置くと、今のコードで測り直して、合計が基準の 1.2 倍を超えたら落とす（速さを変える変更の前後に手元で流す）
- `tests/smb_check.py`・`tests/linux_check.py` は、本物の SMB サーバー・Samba/vsftpd を相手にする手動の試験（使い方は各ファイルの先頭）

- GitHub Actions（`.github/workflows/test.yml`）が、push と pull request のたびに windows-latest で black の確認と pytest を回す。black の設定（行幅 120）は pyproject.toml
- CI が入れる依存の版は `constraints.txt` で固定する（`-c constraints.txt`）。新しい版が出ても CI が勝手に拾って落ちないようにするため。版を上げるときは、手元で上げて全部の試験を通してから表を書き直す（手元の版と表がずれていると、下の確かめが止める）。表は Windows・Python 3.11 の手元から作ったものなので、CI の Python を上げるときは作り直す
- push の前の確かめ: `python tools/prepush_check.py` が、CI と同じこと（コミットしていない変更・add し忘れた .py が無いか・依存の版が `constraints.txt` と同じか・black・pytest 全部）を手元で流す（`--quick` で版と書式だけ）。
  git の pre-push フックにすると、落ちたときに push が止まる（push のたびに約8分かかる。文書だけの push などで飛ばすときは `git push --no-verify`）。`.git/hooks/pre-push` を次の内容で作る（python のパスは自分の環境のもの）:
  ```
  #!/bin/sh
  exec <python.exe> "$(git rev-parse --show-toplevel)/tools/prepush_check.py"
  ```
  CI にしか無い違い（共有の機械で遅い・7-Zip や日本語の OCR が無いので飛ばす試験がある）は手元では見つからないので、時間を測る試験は上限に余裕を持たせる

## ブランチ

- main へ直接コミットしない。作業ごとに `feat/…`・`fix/…`・`docs/…` のブランチを切り、push して pull request を作り、CI が通ってから main へマージする
- Release は main から作る

## リリースの手順

いまは動作を保証できる段階ではないので、Release はすべて**実験版**（GitHub の Pre-release）にし、安定版は付けない。
README のダウンロードの案内は、実験版が出ない `releases/latest` ではなく `releases`（一覧）へ向ける。

1. `pii_checker/__init__.py` の `__version__` と CHANGELOG.md を更新してコミットする（ブランチで更新して pull request を作り、main へマージしてから次へ進む）
2. `python build.py --require-rust` で配布版を作り（拡張を作れなければ失敗になる）、できた `dist/PiiChecker/cmd/PiiChecker-cmd.exe --version` の2行目が「検出エンジン: Rust 拡張」であることを確かめてから、`dist/PiiChecker` フォルダごと `PiiChecker-<版>.zip` に固める
3. `Get-FileHash PiiChecker-<版>.zip`（SHA256）を取る
4. `gh release create v<版> PiiChecker-<版>.zip --prerelease --title "v<版>（実験版）" --notes-file <CHANGELOG の該当の節と SHA256 を書いたファイル>` で Releases に置く（ノートのファイルはリポジトリの外に一時的に書く）

## 対応形式の詳細

- **Excel**: xlsx/xlsm（全シート・非表示/ごく非表示シート・コメント・図形・グラフ・ピボットキャッシュ・外部リンクの控え・文書プロパティ）、xlsb、xls（BIFF8・Excel 5.0/95・2.x〜4.0）、ods。列見出しから列の意味を推定（「氏名」列は辞書に無い名前も拾う）
- **Word**: docx（本文・表・ヘッダー/フッター・テキストボックス・コメント・脚注・変更履歴の削除文字列）、doc（97-2003・6.0/95）、rtf、odt
- **PowerPoint**: pptx（ノート含む）、ppt
- **PDF**: 本文・注釈・フォーム欄（欄名を見出しとして）・しおり・文書情報・添付ファイル。文字の無いページ（スキャン）は OCR
- **画像**: png/jpg/gif/bmp/tif（複数ページ）/webp を Windows 標準の OCR（日本語）で読む。HEIC・AVIF（`sniff` の `image_unsupported`・`misc.handle_image_unsupported`）は PIL で開けないので、WIC（`ocr.open_with_wic`。EXIF の向きを守る `get_software_bitmap_transformed_async`）で開き、開けなければ pillow-heif（任意の追加・入っていれば）で開く。どちらも開けなければ検査不能で、WIC の「部品が無い」（`0x88982F50`）なら Windows の拡張の入れ方を、それ以外は壊れている可能性を理由に出す。pillow-heif の wheel は x265（GPLv2）・libheif・libde265（LGPLv3）を含む約 28MB なので、必須の依存にせず、`build.py` の `excludes` で配布版から外す（試験 `test_pillow_heif_is_not_bundled`）
- **Access**: accdb/mdb/mde/accde（Access 97〜）。64bit ACE ODBC → 32bit 補助（Jet4 ドライバ。Access 97 も読める）→ 同梱の Jackcess（Java。.accdb だけ。読み取り専用で開く。ACE の無い PC 向け）→ 純 Python の順。OLE オブジェクト型の中のファイルも取り出す。ファイル全体の生データ走査で**削除済みレコードの残留**も拾う。元ファイルは一時フォルダへ複製してから開く（NAS 上にロックファイルを作らない）
- **DB**: SQLite（空き領域の残留も）、dBase、PostgreSQL ダンプ（plain/custom/directory/tar。custom は pg_restore が無くても自前で展開）、mysqldump 等の SQL 文（COPY・INSERT を列名つきで）、Oracle の exp/expdp ダンプ（表の行を列名つきで。読み解けない部分は文字列の走査で補い簡易検査。形式は下の「Oracle ダンプの形式」）、SQL Server の bak/mdf・InnoDB 等（簡易検査）、Parquet（`formats/parquet.py`。頭と尾の `PAR1` で見分け、pyarrow で文字の列・入れ子の中に文字がある列・見出し語に当たる列だけを `add_records` へ。数・日付だけの列は読まない（注記に列の数）。pyarrow が import できなければ `misc.handle_unknown`）
- **メール**: eml/mht（ISO-2022-JP 等）、msg（添付も再帰）、PST/OST（簡易検査）
- **アーカイブ**: zip（日本語名 cp932・ZipCrypto/AES）、7z（一覧の暗号化含む）、rar、lzh、cab、arj、tar/tgz/tar.gz/tar.bz2/tar.xz/tar.zst/tar.lz4、gz/bz2/xz/zst/lz4/.Z/lzip 単体、cpio、rpm、deb。入れ子も再帰
- **ディスク・OS イメージ**: ISO、WIM/ESD、VHD/VHDX、VMDK、VDI、QCOW2、DMG、生ディスク（MBR/GPT）、NTFS/FAT/exFAT/ext/squashfs のパーティション。7-Zip で中のファイルを取り出し、一定量ずつ展開→検査→片付け（一時領域を食い潰さない）。BitLocker は検査不能
- **テキスト**: 文字コード自動判定（UTF-8/16・Shift_JIS・EUC-JP・ISO-2022-JP）、CSV/TSV は表として
- **git リポジトリ**（作業フォルダの .git も bare リポジトリも）: 履歴の全オブジェクト（緩いオブジェクト・pack の差分を戻したもの）を検査し、消したファイル・過去の版に残った個人情報も拾う。blob には元のパス名を付けて表示。コミットの作者・メッセージ、索引（index）のパス名も検査
- **その他**: 拡張子に関係なく中身で判定（改名・拡張子なしも）。NTFS の代替データストリーム（隠しストリーム）。構造の分からない形式は文字列走査（簡易検査）、圧縮・暗号化された未知の形式は検査不能

## 設計の考え方

### 言い切れるかどうか

- すべての検査対象（実ファイル・アーカイブの中身・埋め込み・添付・隠しストリーム・DB の表）に、検査済み／簡易検査／要パスワード／検査不能／対象外のどれかを必ず付け、黙って飛ばすものを作らない。開けなかったフォルダと、辿らなかったリンクも記録する
- 構造を解釈できない形式は「検査済み」と呼ばず「簡易検査」と分ける
- 「列挙したファイル数」と「結果のあるファイル数」の一致をレポートに出す（取りこぼしが無い証跡）
- 形式は拡張子ではなく中身で判定する（改名・拡張子なしでも見逃さない）。中身を読まずに「対象外」「検査済み」にする判定は、目印を版のバイトまで照らし、テキストとして読めるものはテキストを先にする（「MZ-100,型番」のような CSV を実行ファイルと誤らない）
- NAS への接続が切れて読めなかったものは「検査不能」で確定させず未検査で残し、続けて切れたら検査を中断する（つながってから再開すれば取り戻せる）。使用中（排他・範囲ロック）も「権限が無い」と出さない。Windows ではどれも PermissionError / FileNotFoundError になるので、元のエラー番号で見分ける
- フォルダの識別子（ボリューム＋ファイル番号）で、同じフォルダへ戻る道（Samba がシンボリックリンクを普通のフォルダとして見せる等）を見分け、リンクとして記録する

### Oracle ダンプの形式

実物（Oracle 21c・AL32UTF8）の解析で分かった形式。読み取りは `pii_checker/formats/oracle_dump.py`、状態の決め方は `dbdump.handle_oracle_dump`。

- **旧 exp**: 文は平文の行。`INSERT INTO "表" ("列", ...) VALUES (:1, ...)` の直後に、列数（2バイト LE）・列ごとの型と長さ
  （VARCHAR2=1・CHAR=96 だけ文字セット ID と形が続く）・`00 00`。その後は行ごとに `00 00` ＋ 列ごとの「長さ（2バイト LE・0xFFFF は NULL）＋値」。
  表の終わりは `00 00 FF FF` の後に次の文の改行。
- **expdp（直接パス・圧縮なし）**: 表ごとに 4KB 境界から列定義の XML（`<STRMTABLE_T>`・列の NAME/TYPE_NUM/LENGTH/CHARSETID）、直後から行。
  行は `3C` ＋ 総長（2バイト BE）＋ 列数（1バイト）＋ 列ごとの「長さ（1バイト・0xFE は続く2バイト BE・0xFF は NULL）＋値」。
- **値**: NUMBER は内部形式（基数 100 の仮数。正は 0xC1+指数、負は 0x3E-指数で末尾 0x66）、DATE は7バイト（世紀+100・年+100・月・日・時+1・分+1・秒+1）、
  文字は列の文字セット（CHARSET_CODECS に表）。LONG・LOB・RAW・知らない文字セットの値は読まず、バイト列を文字列の走査へ回す。
- **取りこぼさない作り**: 表として読めなかった部分（表の外側・壊れた行以降・知らない型の表・未対応の値）は `_GapSweeper` が従来どおり文字列として走査する。
  全部の表を読み解け、表の外側のゼロでないバイトが `GAP_NONZERO_LIMIT` 以下のときだけ「検査済み」。それ以外（切れたダンプ・未対応の列・読めない表）は簡易検査で、理由に何が読めなかったかを書く。
- 圧縮（COMPRESSION=ALL/DATA_ONLY）・暗号化の expdp は行が KGC 形式などになり表として読めないため、従来どおりエントロピーで「検査不能」にする。

書き換え（対処。`pii_checker/remedy_oracle.py`）のために、実物（Oracle 21c XE で作った、5 つの表・それぞれ 30 万〜100 万行の旧 exp・expdp。1.6GB）で突き止めた形:

- **expdp のファイルの作り**: 4096 バイトのブロックの並び。ブロック 0 はファイルの見出しで、**+0x36 に BE32 で「マスターテーブルの開始ブロック番号」**（実測: 1625489408 / 4096 = 396848）。
  見出しの後ろは「単位」の並び。単位 = **制御ブロック**（4096 バイト。先頭 `ff ff 24 24`）＋ **本体**（ブロック境界から）。マスターテーブル（`SYS_EXPORT_SCHEMA_01`）も同じ作りで最後にある。
  - 制御ブロック: `ff ff 24 24`・種別 2 バイト（表のデータ `0a 00`・メタデータ `14 04`）・6 個の 8 バイト BE（+6 から）F1..F6・残りはゼロ
  - 表のデータの本体: 先頭 `03 69` ＋ XML（`<?xml…</ROWSET>`）= **F1** バイト → 次の 8 バイト境界 align8(F1) から行（`3C` ＋ 全長 BE16 ＋ 列数 ＋ 各列「長さ（1バイト。0xFE は続く 2 バイト BE・0xFF は NULL）＋値」）が **F3** バイト → 次の 8 バイト境界から**索引**（8 バイト BE の並び）が **F5** バイト → ブロック境界までゼロ
  - 値の意味（5 つの表すべてで一致を確認）: F2 = 4096（制御ブロックの大きさ）／ F4 = align8(F1) + 4096（行の始まり。制御ブロックの先頭から数える）／ F6 = align8(F1) + align8(F3) + 4096（索引の始まり。同じく制御ブロックの先頭から数える）
  - **索引** = [0, e1, e2, …]。行の始まりからの相対で、e(k) は「e(k-1) + 10,240,000 以上で最初の行の境界」（電柱: 0, 10240111, 20480262, …。差はすべて 10,240,000 以上。境界 20480000 があっても e1 + 10,240,000 = 20,480,111 に届かないので選ばれない）。行の終わりちょうどは含めない。並列で読み込むための粒度の印と思われる（用途は未確認）
  - 単位の本体の大きさ = (align8(F1) + align8(F3) + F5) をブロックの倍数に切り上げた長さ。その次のブロックが次の単位の制御ブロック
- **メタデータ（DDL・統計）は `KGC` の圧縮ブロック**（ブロック 1・3〜5。`COMPRESSION=METADATA_ONLY` が既定のため）で、マスターテーブルの XML_CLOB なども同様と思われる。圧縮の方式は公開されておらず書き換えられないので、
  expdp の**列の削除・表の削除は対応しない**（行の削除・ダミー化だけ）。メタデータの統計には列の最小値・最大値が入りうるが、書き換えられないので残る（下見・README に出す）
- 行の削除・ダミー化は、ファイルの大きさを変えずに（マスターテーブルが各単位の位置を持つので、ずらさない）行を詰め直して、F3（行の合計）・F5（索引の大きさ）・F6（索引の始まり）と索引（新しい行の境界から同じ規則で作り直す）を直し、残りをゼロで埋める。F1・F2・F4・XML・ほかの単位は変えない。
  書き換えの前に、元の単位が上の式を満たし（F の値・行の合計がちょうど F3・元の索引が規則どおり・ゼロ詰め・次が制御ブロック）、満たさなければ断る。ダミーは元の値より長くしない（行が増えて単位に収まらなくなるのを防ぐため。収まらないダミーは同じバイト数の英数字、短すぎる値は `*`）。
  **imp／impdp が通るかは、この環境では確かめていない（Docker の Oracle での確かめの台本を別に用意した）。マスターテーブル側の行数の記録（COMPLETED_ROWS など）と書き換え後の行数が食い違うこと、制御ブロックの値以外に索引・行の合計を使う場所があるかどうかが、確かめるべき点**
- **旧 exp の区画の並び**（実物）: `\nTABLE "表"\n` → `CREATE TABLE "表" (列の定義, …) PCTFREE …\n` → `INSERT INTO "表" (…) VALUES (:1, …)\n` → 列の定義 → 行 → `00 00 FF FF` ＋ `\n` →
  続く文（`ANALSTATS TS "表"\n` ＋ 長さ（2 バイト LE）つきの PL/SQL。表の統計と列ごとの統計。**列の統計の `SREC.MINVAL`・`MAXVAL` に、列の最小・最大値の 16 進が入る＝元の値が残る**）→ 次の表。最後の表の後ろに `ENDTABLE\n`、続けて表ごとの
  `TABLE "表"\nANALCOMPUTE TS "表" ANALYZE TABLE "表" ESTIMATE STATISTICS \n`（2 周目）・`ENDTABLE\n`・`EXIT\n`。文の長さの前置きに改行の値が混ざりうるので、区画の切れ目は行頭のキーワード（`TABLE "`・`ENDTABLE`・`ANALSTATS `・`ANALCOMPUTE `・`CREATE `・`ALTER `・`GRANT `・`COMMENT ` など）で見る。
  索引・制約・コメント・権限の文の実物は、手元の検体（CREATE TABLE AS で作った表）に無く、形は推測（`CREATE [UNIQUE] INDEX "名" ON …`・`ALTER TABLE … ADD CONSTRAINT …`・`COMMENT ON COLUMN …`）。読み取れない・使い方が分からない文が削除する列を使っていれば、列の削除を断る

### 検出

- 生データ走査（削除済みレコードの残留）の検出は確度を1段下げる（値の区切りが失われて取り違えうるため）
- base64 の埋め込みは、ファイルの目印があるか UTF-8 の文字として読めるときだけ取り出す（cp932 で読むと乱数でも仮名に見えるため）
- 左隣のセルを見出しとみなすとき、値まで入ったセルは「弱い見出し」として確度を下げる（見出しから外すと見落とす）
- 住所・固定電話は、同じファイルに人の手がかり（確度 中以上の氏名・生年月日・重要な種類・携帯・語つきの電話、または「名簿」「履歴書」などの題）があるときだけ 中、無ければ 低（要確認）。公共施設の所在地や番地の一覧を「可能性あり」にしないため。拾わない（消す）ことはしない
- FAX の語は会社の番号の手がかりにしない（個人の連絡先にも並ぶため）
- 自分で足す規則（利用者の規則）の正規表現は、Python の re が途中で止められないため、受け付ける前に断る: 200 文字まで・後方参照と入れ子の繰り返しを断る・長さ0に当たるものを断る・同じ文字に当たる長い繰り返しの連続（`.*.*x`・`[a-z]{1,200}[a-z]{1,200}!`。上限が 16 を超える `{m,n}` は上限なしと同じに扱う）を断る・繰り返しの中で当て方が何通りにもなる選択肢（長さの違う選択肢・1文字目が重なる選択肢。`(a|a)` は構文解析で `a(?:|)` にくくられるので、長さ0の選択肢が2つ以上あるものも数える）を断る・繰り返しの文字列に実際に当てて遅いものを断る。速さは、1024 文字の試し文字列1本の時間を、この PC で測った基準の正規表現（`\w+@`）の4倍まで受け付ける（PC の速さに左右されない。この PC では約 10ms）。試し文字列1本が 50ms を超えたら長さに関わらずすぐ断るので、受け付けで待たせない。検査では1回に 1024 文字ずつ当てる。それでも通り抜けた遅い書き方は、1ファイルの時間制限で「検査不能（時間切れ）」になる（黙って飛ばさない）
- 自分で足す規則は re.MULTILINE で当てる（速さを確かめる段も同じ）。正規表現の全体を NFKC で寄せず、全角の英数字だけを半角にし、全角の記号はその文字（本文と同じく NFKC で寄せた文字）を逃がして当てる（全体を寄せると「（本社）」がグループに、「＊」が繰り返しに化ける）
- 拾わない値（許可リスト）は正規化（全角→半角・空白・ハイフン・括弧を除く・氏名は敬称を外す）して完全一致だけを外す。外した件数は必ず判定とレポートに出す
- 異なる値はワーカーのメモリで数え、数だけを items.distinct_counts・files.distinct_counts に保存する（値もハッシュも残さない）。
  報告の目安の印は保存した件数から決め直せるので、reportflags・folderacl・jobdiff は検査器の版（signature の除外）に含めない
- アクセス権は READ_CONTROL と BACKUP_SEMANTICS だけでフォルダを開いて読む（一覧も中身も読まないので日時を変えない）。同じフォルダは1回だけ読む。
  Samba は Unix の権限を NT の ACL に写して見せるので、本物の NAS での見え方は確かめていない（目安として扱う）。
  中のファイルに届く項目（OBJECT_INHERIT を含むもの・継承の指定の無いフォルダ自身の項目）だけを数え、サブフォルダにだけ継承される項目（CONTAINER_INHERIT だけ）は数えない。
  見つからなければ「広い許可なし（目安）」と出し、「限られた人だけ」とは言い切らない（全社員グループ・Samba の Unix のグループ・ファイル個別の ACL は見ていない）
- 所有者の名前は、よく知られた SID（S-1-1-0・S-1-5-18・S-1-5-32-… など）と、この PC のアカウントの SID（NetUserModalsGet で得たこの PC の SID で始まるもの）だけ LookupAccountSidW で引き、ほかは SID の文字列のまま出す（ドメインの SID を引くとドメインコントローラーへ問い合わせが飛び、「検査先を読むほかはどこにも接続しない」を破るため）
- 前回との違いは、FTP 以外は os.path.normcase で寄せたパスで突き合わせる。前回と今回で結果に効く設定（signature と同じく、場所・道具・使い回しの指定などを除いたもの）か検査器の版（files.engine_sig）が違えば、違いの要約に添え書きを付ける。今回の検査の folder_errors（開けなかったフォルダ・辿らなかったリンク）の下にあった「無くなった」ファイルは「今回は調べられなかった」にする
- 報告の目安のジョブ全体の合計は、異なるマイナンバーは files.distinct_counts を足したもの（ファイルをまたいだ重なりは値を残していないので除けない＝上限の目安）、人数の目安は files.people_n を足したもの（ファイルごとに選ぶ種類が違いうるので、多くも少なくも出る＝上限とは言わない）。人数の目安の種類は reportflags.PEOPLE_TYPES の順を優先にして、数が同じなら先の種類を選ぶ
- 利用者の規則は、種類の件数（items.counts・conf_counts）は custom のまま、規則の名前ごとの件数を items.rule_counts に、異なる値を「custom/規則の名前:確度」の鍵で distinct_counts に持つ（画面の内訳・異なる値を規則ごとに出すため）。照合の前に CR LF・CR を LF に寄せ、位置は元の本文に戻す
- 速さのため、氏名（敬称つき・空白区切り）は後ろ読みのある1本の正規表現をやめ、後ろ読みの無い前ふるいで候補を拾ってから漢字かどうかを判定する。敬称（様・殿・さん など）や空白が本文に1つも無ければ、その規則は走らせない。重なりの除去（`_dedupe`）は位置で二分探索する。どれも直す前と後で全検出を書き出してバイト単位で一致することを確かめ、tests/test_detect_speedup.py で元の書き方との同値を押さえている
- 代替データストリームを持てるボリュームかを引くための、フォルダごとのボリュームの根（GetVolumePathNameW は1回約 6ms）は `lru_cache`（512 件・失敗は覚えない）で覚える。検査中の進み具合は件数だけを数える `store.progress` で出し、要約は `store.summary_cached` で、計算にかかった時間の4倍（最短 1.5 秒・最長 30 秒）の間だけ前の値を使い回す（1万件で要約に 10 秒かかっていたため）
- zip として開けない Office（xlsx・docx 等）・zip は、7-Zip の生の出力を理由に出さず、利用者向けの文を理由に、一時フォルダのパスを除いた短い技術情報を補足に置く（formats/archive.broken_archive）

### 読み取り

- 元のファイルは読むだけ。Access・SQLite は一時フォルダへ複製してから開く（NAS 上にロックファイルを作らない）
- Access は 64bit ACE ODBC → 32bit 補助（Jet4）→ 同梱の Jackcess（Java。.accdb だけ。補助の `openro`・`readall` 命令）→ 純 Python の順に試す。試験では `database.FORCED_READERS`（環境変数 `PIICHK_ACCESS_READERS`。odbc・helper32・jackcess・parser のコンマ区切り）で読み方を絞れる。32bit 補助は標準ライブラリだけで動かし、配布版ではPython 公式の 32bit 埋め込み版を同梱する（pip 不要）
- Access の ODBC 接続文字列では、値を波括弧で囲むとパスワードが一致しない（ACE の癖）。`;{}` を含むときだけ囲む
- ツール本体は Office の COM を使わない（サービス等のセッション0から動かすと Office の COM は失敗する。Office の無い PC でも動く）
- DB へ直接つないで検査する機能は持たない。DB はダンプ・ファイルとして検査する（フォルダの下のファイルを調べる道具に絞る）
- ディスクイメージは一定量ずつ展開→検査→片付けを繰り返す（一時領域を食い潰さない）
- git の pack は過去の全版を戻して調べるので、時間制限を通常の4倍にしてある
- HTML に data URI で埋め込んだ画像も画像として検査するので、OCR を無効にすると検査不能の項目になる

### 接続方式

- SMB は自前の SMB 実装を持たず Windows の接続に任せる（共有をすべて許す開き方・日時を保つ・使用中や回線断の見分けを、フォルダ指定と同じ部品で使えるため）。SMB の接続方式ではポートを変えられない（Windows の SMB クライアントの仕様）
- FTP は標準ライブラリの ftplib。FTPS はデータ接続でも TLS のセッションを使い回す（vsftpd 等は使い回しを求める）
- FTP の一覧は MLSD → `LIST -a` → `LIST` の順に試し、隠しファイルが見えているか確かめられないサーバーではそのフォルダを要対応にする。分割アーカイブの続き・隠しストリーム・pg_dump の隣の toc.dat は取りに行かない
- 接続に失敗した理由はすべて日本語にする（パスワード違い・共有名違い・別ユーザーで接続済み（1219）・証明書・方式の違い等）
- 接続のパスワードは保存しない。覚えたパスワードを捨てるのは、パスワードを断られたとき（FTP 530・SMB 86/1326/1330）だけで、回線断では残す。サーバーは失敗の応答に印（`X-Pii-Needs-Password`・`X-Pii-Network`）を付け、画面は印で案内を出し分ける

### 画面

- GUI は tkinter を使わず、Web 版と同じ HTML/CSS/JS を pywebview で表示する
- Web 版は既定で 127.0.0.1 だけで待ち受け、起動ごとのランダムな合言葉・Host ヘッダーの検査・書き込みの要求には独自ヘッダー（`X-Requested-With`）を求める（ほかのサイトからの要求で操作されないため）。ほかの PC から使うときは `--host` と `--token` が必須
- pywebview の js_api に渡すオブジェクトは、画面から呼ぶメソッド以外の属性をすべて `_` で始める（pywebview は `_` で始まらない属性を再帰的にたどるので、窓などを持たせると exe で固まる。tests/test_desktop.py で公開名を固定している）
- WebView2 ランタイムは同梱しない（Windows 11 は標準で入っている。無ければ同じ画面を既定のブラウザで開く）

### 検出した値の表示（reveal）

- 保存・レポートは伏せた値だけ。画面の詳細は、そのファイルを `engine.scan_file` で読み直して生の値を返す（`reveal.py`・`POST /api/jobs/{id}/reveal`）。設計の要点:
  - `ScanOptions.reveal=True` のときだけ `Finding.raw_value`・`raw_context` を入れる。`reveal` はジョブの設定として保存せず（`store.create_job` が外す）、検査器の版（`signature._OPTION_EXCLUDE`）にも含めない。`store.save_result` は `raw_*` を書かない（tests/test_reveal.py が DB・レポート・一時フォルダのバイト列を生の値で探して確かめる）
  - reveal の読み直しは途中経過（checkpoint の pickle）を書かず、消しもしない（生の値が一時フォルダに出ない・通常の検査の途中経過を壊さない）
  - 読み直しは pebble の別プロセス（`procguard.worker_init` のメモリ上限・時間制限つき。大きさ÷512KB/秒と 10 分の長いほう）。結果は `(項目のパス, 種類, 場所, 伏せた値)` で DB の明細と突き合わせ、`findings` の rowid ごとに返す。突き合わない明細は返さない（画面は「元のファイルが変わったため表示できません」）。更新日時・SHA-256 が検査時と違えばその旨も返す
  - パスワードは検査を動かしているメモリの `PasswordBook` の写しだけを使う（無ければ要パスワードの項目は表示できない）。FTP は接続のパスワードをメモリに持っているときだけ読み直せる
  - 結果はサーバーのメモリに 10 分・30 件まで（ディスクには書かない）。画面は読み直しを始めて、1秒ごとに状態（running / done / error）を見に行く

### 検出した個人情報への対処（remediate）

- 検査（scan）は何も書き込まない。対処は人が画面で選んで実行したときだけ（`remediate.py`・`remedy_write.py`・`/api/jobs/{id}/remedy/*`・`/api/jobs/{id}/remediations`。ほかの API と同じトークン・Host・`X-Requested-With` の守りの内側）。設計の要点:
  - 位置の集め直し: `ScanOptions.collect_positions=True` のときだけ `engine.Collector` が、各検出の構造の位置を上限なし（メモリの上限として `POSITIONS_LIMIT` = 200 万件で「多すぎる」）で `ItemResult.positions` に集める。キーは（シート名, 種類, 確度の順位）、値は（行, 列, 値の開始, 値の終了）を並べた `array('q')`。csv・tsv は行・列、txt は行（`pos_layout`）、xlsx はシート・行・列。生の値は持たない（ダミー化のとき、書き換える側がセルの文字を読み直して位置の部分だけを置き換える）。開始・終了は NFKC 正規化後の位置なので、`remedy_write.replace_spans` が元の文字の位置へ直す（直せないときはセル・行の全体をダミーにする）。人の手がかり待ちの住所・固定電話は、`finish()` で 中／低 に振り分ける。`reveal` と同じく、ジョブの設定として保存せず（`store.create_job` が外す）・検査器の版（`signature._OPTION_EXCLUDE`）にも含めず・途中経過を書かない
  - 別プロセス: 位置の集め直し（`collect_task`）と、実行のうち元に触らない部分（`apply_task`＝一時の新ファイルを書いて検査し直す。ファイルの削除もここ）は pebble の別プロセス（`procguard.worker_init` のメモリ上限・時間制限）。元の名前への確定（`commit_rewrite`）・記録の更新・立て直しは親のプロセスが行う。試験は `runner_fn=inline_runner` で同じ関数をその場で走らせる。分析の結果（位置の集まり）はサーバーのメモリに 10 分・4 件まで
  - 実行: `_begin_run` が前提を確かめ、同じファイルの止まった記録を立て直し（`recover`）、書き換えなら `store.add_remediation(state="started", note=段取りの JSON)` で記録を作る（段取り＝`make_commit_plan`: 方法 recycle / replace / convert・一時の新ファイル `~piichk-new-<英字8字>-元の名前`・改名後の元 `元の名前（対処前 日時）.拡張子`）→ `apply_task`（別プロセス）が実行の時点でもう一度読み直して位置を集め、下見のときの SHA-256 と違えば断り、一時の新ファイルへ書いて fsync し、`rescan_summary` で開けること・残りを確かめる → `commit_rewrite`（親）が元がまだ同じか確かめ、recycle は「元を改名 → 新を元の名前へ → 改名した元をごみ箱へ」、replace は `os.replace`、convert は「zip を置く → 元の書庫を消す」。各段のあとで `remediations.state` を started → renamed → swapped → applied と進める。普通の失敗（Exception）はその場で元へ戻して記録を消す。Exception でないもの（強制終了）はわざと捕まえず、落ちた状態を残す（試験は `SimulatedCrash(BaseException)` で各段の直後に落とす）
  - 記録は `remediations` 表（時刻・ファイル・方法・絞り込みの種類と確度・変わった数・元のファイルの行き先 `disposal`・残り・元と新の SHA-256・状態・段取りと立て直しの説明 `note`）。元の写しは作らないので `backup_path` は常に空。値は書かない（tests/test_remediate.py が DB・WAL のバイト列を生の値で探して確かめる。陽性対照つき）
  - 検査し直しでは、この回で作ったダミーそのもの（`DummyMaker.produced`）を許可リストの仕組みで数えない（列見出しが「メール」「氏名」の列は中身が何でも値として拾う規則があるため）。保存しない
  - csv・tsv・txt: 文字コードは BOM・UTF-8・cp932・EUC-JP・UTF-16 を、元のバイト列へ正確に戻せるときだけ扱う（`decode_for_rewrite`）。csv のレコードは `csv.reader` と同じ読み方で元の文字列のまま取り出し、触るレコードだけ欄を元の書き方（引用符の有無）のまま組み直す。txt は `str.splitlines` の行（検査の行番号と同じ数え方）
  - xlsx: 行・列・シートの削除は openpyxl で読み込み直して保存する（`_delete_rows`・`_delete_cols` はセル・結合・行の高さ・列の幅・リンクの位置を詰める。数式の参照・条件付き書式・入力規則は直さない）。ダミー化は zip の中のシート XML の対象セルだけを正規表現で書き換え（`inlineStr`）、使われなくなった共有文字列は空にする。それ以外の部品はバイト単位で同じ
  - ファイルの削除（`delete_original`）は**元の写しは作らない**: ごみ箱のある場所（`has_recycle_bin`）は `send_to_recycle_bin`（`SHFileOperationW`＋`FOF_ALLOWUNDO|FOF_NOCONFIRMATION|FOF_SILENT|FOF_NOERRORUI`。ctypes）、ごみ箱の無い場所（ネットワーク・外付け）はそのまま消す。どちらかを `changed["disposal"]`（`recycle_bin` / `permanent`。書き換えは `recycle_bin` / `replaced`）に残し、下見の1行目（`disposal_text`）・結果・記録（API の `disposal`・`pre_name`）に出す。「元に戻す」（`undo`）と元の写しの置き場は廃止した。試験は autouse の `trash` 固定具で `remediate.has_recycle_bin`・`send_to_recycle_bin` を差し替える（本物のごみ箱へは送らない）
  - 立て直し（`recover_record`・`RemedyService.recover`）: 記録が started / renamed / swapped のままのものを、ファイルの今の状態（元の名前・「対処前」の名前・一時の新ファイルの有無と SHA-256）から立て直す。起動時（`create_app`）と、同じファイルの対処を始める前（`_begin_run`）に走る。元の名前が無く「対処前」があれば戻す／一時の新ファイルが残っていれば消す／新が入っていて改名した元が残っていればごみ箱へ送り直す／判断できなければ両方残す。結果は記録の状態（applied / recovered）と説明（`/remediations` の `recovery`）に出る

### 実測で分かった限界

- Samba は最終アクセス日時を保つ指示（SetFileTime -1）を守らず、読むとサーバー側の日時が更新される。Windows のクライアントがファイル情報を約 10 秒手元に持つので、読んだ時点では見抜けない。ツールの記録（atime_kept）は「保つ指示を出した」までを意味する
- Samba は変更日時として更新日時を返す（Linux の ctime は SMB から見えない）ので、大きさと更新日時を保ったままの書き換えは見抜けない
- FTP にはフォルダの識別子が無いので、リンクを辿って見せるサーバーのループは 64 段の深さで止めてリンクとして記録する
- git の SHA-256 リポジトリで、pack の差分の元をハッシュで引くもの（REF_DELTA）は戻せないことがある（その pack は検査不能）
- BOM の無い UTF-16 で罫線・絵文字が多いテキストは「簡易検査」になる（バイナリをテキストと誤らない側に倒している）

    - 効く場面: 上の `PendingQueue` の後の模擬では、2026-11-02 の実物でワーカー8本 11,348 秒・下限（合計 89,670 秒÷8）11,209 秒、6本 15,071 秒・下限 14,945 秒で、分けて縮むのは約1%だけ。いちばん長い 7.8GB の zip（6,245 秒）が下限より短いため。分けて効くのは、1つの書庫の検査時間が合計÷本数を超える形（ワーカーが多い・ドライブの時間の大半が数個の大きな書庫）と、実測（24,474 秒）と模擬の差が終わりの区間で1本だけ動く時間にあると分かったときだけ
    - 分ける対象: 実ファイルそのものが `runner.BIG_FILE_BYTES`（1GB）以上の zip（Python の zipfile で読めるもの＝暗号化なし・`SUPPORTED_ZIP_METHODS`）と無圧縮の tar だけ。中の項目へ直接飛べる形に限る。gz・bz2・xz の1本の流れ、solid の 7z・rar、7-Zip を通す暗号化 zip は分けない（先頭から順に解くしかなく、分けると同じ所を何度も解く）。値を持つ読み直し（`reveal`）・位置集め（`collect_positions`）・対処の検査し直しも分けない（1本の経路のまま）
    - 区切り方: 目次（zip の中央ディレクトリ・tar の見出し）だけを読み、展開後の大きさで約 512MB ずつ（項目の並びの順を保ったまま）にまとめる。1項目が大きいものは1区切り。区切りが2つ未満なら分けない。区切りの数は展開後の大きさで決まるので、圧縮の効いた書庫ほど多くなる
    - 写しは1回: 元のファイルの写し（`safeio.snapshot`）と SHA-256 は、今と同じくワーカーの中で作る（配る側のスレッドで 7.8GB を写すと、その間ほかのファイルを配れない）。配る側はファイル単位で配った時点では分けるかを知らない。ワーカーの `scan_file` が目次を読んで分けると決めたら、区切り0を検査せずに「計画」（写しのパス・SHA-256・区切りの一覧・目次から求めた `_torch_dirs` の結果）を返す（区切り0まで最初の仕事で検査すると、それが終わるまで残りを配れない）。今の `_save_result` は `FileResult`（`items`・`network_lost` など）しか受けないので、計画を受けて区切り0を含むすべての区切りを配る分岐を足す。写しの一時フォルダと持ち主の目印（`OWNER_MARK`）は、`runner.BIG_FILE_BYTES` 以上で拡張子が zip・tar のファイルにだけ、配る側が先に作ってパスを渡す（今はワーカーの `ScanContext` が作り、`scan_file` の終わりの `cleanup()` で消す。ワーカーが作って後から配る側へ渡す順だと、目印が閉じてから開くまでの間に後始末の掃除が写しを消しうる）。計画を返す仕事は写しを消さない。写しは最後の区切りが戻った（打ち切りを含む）ときに配る側が消す（参照の数を数える）。目印を配る側が開いたままにするので、後始末の掃除（`cleanup_stale_temp`）には消せない。検査の停止・中断・保存の失敗・計画を返す仕事の時間切れや異常終了でも配る側が消し、分けないと決まったとき（7-Zip の経路・壊れた目次）は先に作った一時フォルダをその仕事に使わせて今と同じく終わりに消す
    - 区切りの仕事: `scan_archive_part(写し, 元のパス, 項目の番号の範囲, options, book)`（番号は `handle_zip` の `infos`＝ディレクトリを除いた項目の並びでの位置） が、今の `handle_zip` のループの中身（`_read_zip_member` → `_scan_extracted`）を範囲の分だけ回す。内側の書庫の再帰・時間制限・途中経過（checkpoint）は区切りごと。今の `JobRunner._timeout_for(path)` はファイルの大きさから決めるので、区切りの展開後の大きさを渡す引数を足す。途中経過の鍵（`checkpoint_path(options, top_path)`）もパスだけで決まるので、区切りの番号を足す。書庫の全体の一覧を見る判定（`_torch_dirs`）は、計画に入れた結果を各区切りへ渡す
    - 1つのファイルにまとめる所: 保存は今と同じく1ファイル1行（`FileResult`）。今の `JobRunner._save` は検査の future を1つ受け取る形なので、区切りの結果を項目の番号の順に並べて渡す受け口を足す（明細の並びと項目のパス「外!内!…」は分けないときと同じにする）。ファイル全体の異なる値の数（`ScanContext.distinct`）は区切りをまたいで重なるので、区切りは数ではなく（種類 → 値の hash → 確度の順位）を返し、配る側で合わせてから `_count_by_rank` で数える。**今の hash は Python の組み込みの `hash()`（`engine.py` の `seen` の値の4つ目）で、文字列の hash はプロセスごとに種が変わるため、そのままでは区切りをまたいで合わせられない**。区切りをまたぐ hash は安定な 8 バイト（blake2b など）にし、分けないときの経路も同じ関数にそろえる。返すのは `dict` でなく種類ごとに hash の配列（`array('q')`・8 バイトを符号付きに収める）と確度の順位の配列（`array('b')`）にする（異なる値 100 万で約 9MB。今の `dict[str, dict[int, int]]` のまま返すと数十 MB を超える見込み）。合わせた後も上限は `SEEN_LIMIT`（300 万）で、区切りの順に足して上限で止め、超えたときの数え方を分けないときと同じにする。上限に届いた後も既にある値の確度は上げ続ける今の決まりも、合わせるときに同じに扱う。blake2b は新しい値を覚えるたびに呼ぶので（異なる値の数だけ・1ファイルで検出 330 万件の例がある）、分けない経路の費用の増え方も測る
    - 上限: 展開の合計（`max_expand_bytes`）と項目数（`max_entries`）はファイル全体の上限なので、目次の大きさの合計で先に確かめ、超えれば分けずに今の経路へ回す（今と同じ所で打ち切る）。内側の書庫の分は区切りごとに数え、配る側が足して上限を超えた時点で残りの区切りを取りやめ、ファイルを「打ち切り」にする
    - 配る数: 今の `BIG_FILE_CONCURRENCY`（2）は大きなファイルを同時に配る全体の本数。区切りをこの枠に数えると全体で2本しか動かず分ける意味が無いので、区切りは枠の外にし（ファイルの枠そのものは、計画が戻った時点でなく最後の区切りが戻るまで持つ。持たないと 7.8GB 級の写しが同時にいくつも溜まる）、新しい定数（1ファイルあたり同時に動かす区切りの本数）で絞る。一時フォルダの空き（`ensure_space`）は区切りが同時に取り合うので、この本数分を見込む。ワーカーが4本未満のときは分けない（今の大きなファイルの枠も1本になる）。小さいファイルが尽きたら上限を超えて配る今の決まりはそのまま
    - 失敗: 1つの区切りが落ちた（メモリ・時間切れ・ProcessExpired）ときは、その区切りの項目だけを検査不能（途中経過があれば「途中まで検査」）にし、ほかの区切りの結果は残す。回線断は写しを使うので起きない
    - 試験: (1) 分けたときと分けないときで、明細（項目のパス・種類・確度・件数）とファイル全体の異なる値の数が一致する（陽性対照の総当たりの書庫を `runner.BIG_FILE_BYTES` を小さくして分ける・別々のプロセスで動かす） (2) 区切りの1つを落としたときに、その区切りだけが検査不能になる (3) 写しが最後に消える・打ち切り・検査の停止・計画を返す仕事の異常終了でも残らない (4) 上限を超える書庫が分けないときと同じ理由で打ち切られる (5) 異なる値が `SEEN_LIMIT` を超える書庫で、分けたときと分けないときの数が一致する
    - parquet も同じ形で、行グループ（`pyarrow.parquet.ParquetFile.read_row_group`）を区切りにできる（11-06 の保存の遅さが集中した 1GB 級の parquet）。列の見出しの判定（`engine._ColumnDigits`）が表の全体を見るので、区切りをまたぐ判定の合わせ方を別に決めてから
